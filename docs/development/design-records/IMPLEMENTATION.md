# ssmm 実装アプローチ

> [!NOTE]
> 本ドキュメントは実装前の計画であり、各段階の実装完了を示すものではない。現行の開発手順と検証範囲は [開発ガイド](../README.md) を参照。

本ドキュメントは、ssmm の初版を段階的に実装する手順と、各段階を完了と判断する検証条件を定義する。認証、検索の完全性、端末と外部プロセスの挙動を先に確認し、その結果を接続と転送の実装へ適用する。

## 前提と成果物

実装の対象は、商用 AWS の EC2 を扱う Go CLI である。動作確認対象は Linux、macOS、WSL とする。AWS CLI v2、Session Manager plugin、OpenSSH を必要な操作の外部依存として扱う。

機能の受け入れ条件の詳細は、[DESIGN.md の Go の構成と検証](DESIGN.md#go-の構成と検証) を参照。パッケージ間の契約、検索の状態管理、プロセス管理の詳細は、[ARCHITECTURE.md](ARCHITECTURE.md) を参照。

ファイル単位の実装とインターフェースの詳細は、[CODE_STRUCTURE.md](CODE_STRUCTURE.md) を参照。既存設計の不整合、根拠、未検証の互換性の詳細は、[DESIGN_REVIEW.md](DESIGN_REVIEW.md) を参照。

実装は以下の順序で進める。先行段階で得た検証結果を後続段階の完了条件に含め、単にパッケージを作成したことを完了としない。

## 実装手順

### 1. 外部依存と実行境界の検証

本体の実装前に、認証経路と OpenSSH の引数解釈を小さな検証プログラムで確認する。この段階で検証に使用した Go、AWS CLI、plugin、OpenSSH、シェルのバージョンを記録する。

検証対象と完了条件を、以下に示す。

| 対象 | 完了条件 |
| --- | --- |
| AWS の認証経路 | 明示プロファイル、AWS_PROFILE、環境認証、SSO、AssumeRole、credential_process について SDK と CLI が同じアカウント・意図したロールを選ぶ |
| 認証の競合 | 環境のアクセスキーと明示プロファイルが併存する場合、および内部 proxy を経由する場合に認証経路が変わらない |
| 対話認証 | SDK の直接の MFA AssumeRole を対応済みとせず、追加入力が必要な経路では proxy の標準入力を読まず失敗する |
| プロファイルの存在 | 未定義プロファイルの明示指定は失敗し、環境認証だけの既定経路は共有 default 設定なしでも動作する |
| ProxyCommand | 空白、引用符、ドル記号、% を含む固定引数を、OpenSSH とシェルを通して同じ値で受け取れる |
| SSH の設定 | ssh -G で HostName、Port、User、IdentityFile、ProxyCommand、ControlPath を確認し、Host * の HostName による書き換えと鍵の追加動作を検証できる |
| ホスト鍵 | 標準経路の複数ホストが同じ HostKeyAlias を共有せず、ラッパーの別名がリージョンと ID で分かれる |
| プロセス制御 | 操作端末とパイプ入力を分離でき、子プロセスの終了・Ctrl+C・SIGHUP・SIGTERM 後に端末を復元し、入れ子の proxy の子を終了できる |
| Session Manager の通信 | AWS-StartSSHSession 経由で SSH 接続が成立し、ssmm の表示が通信へ混入しない |

認証の比較には検証用の STS GetCallerIdentity を使う。同じロールでも SDK と CLI が別の AssumeRole セッションを作るため、セッション名の完全一致を要求しない。STS による比較を製品の通常起動経路へ追加しない。

AWS 上の検証が必要な項目は、検証用プロファイルと EC2 を使う結合テストとして残す。モックの成功を実際の SSO や Session Manager の互換性の証拠にしない。

### 2. コマンド、設定、対象モデルの実装

Go module とビルド手順を作成し、Cobra、AWS SDK for Go v2、Bubble Tea、TOML パーサーを選定する。Cobra と Bubble Tea は指定された機能構成を維持し、TOML パーサーは未知キーの検出と未定義・空配列の区別ができるものを採用する。

Bubble Tea は v2 系を第一候補とする。公式の [go.mod](https://raw.githubusercontent.com/charmbracelet/bubbletea/main/go.mod) と [利用例](https://github.com/charmbracelet/bubbletea) を参照し、採用するリリースの Go 要件と API を確認する。開発ブランチの依存を固定せず、検証したリリースを go.mod と go.sum に記録する。Go の最低バージョンとビルド用パッチバージョンもこの段階で固定する。

この段階で作成する内容を、以下に示す。

- エントリーポイントと Cobra のコマンド構造
- TOML の読み取り、設定の優先順位、検証
- ProfileSelection、SearchScope、Instance、ResolvedTarget の型
- ID 判定、Name 完全一致、タグ条件、部分一致、安定ソート
- 引数・設定エラーと終了コードの対応

型の所有先は CODE_STRUCTURE.md に合わせる。app の import を target、inventory、execplan に限定し、アダプターの型を引数へ持ち込むことで循環依存を解決しない。ProcessSpec と公開 JSON の ListRow は別の型として作成する。

AWS クライアントや端末を使わず、純粋な判定と設定解決を単体テストできることを完了条件とする。Name と予約されたサブコマンド名が一致する場合に connect で指定できること、-p と SSH のポート指定を混同しないことも確認する。

### 3. リージョン取得と list の実装

awsconfig、awsapi、inventory を実装し、まず list で検索処理を利用可能にする。EC2 全件取得の完了判定を自動接続の実装より先に確定する。

検証対象と完了条件を、以下に示す。

| 対象 | 完了条件 |
| --- | --- |
| 検索範囲 | 指定範囲だけを検索し、未有効化リージョンと DescribeRegions 失敗をエラーにする |
| ページネーション | EC2・SSM の複数ページを最後まで読み、空ページと継続トークンを正しく扱い、トークンの反復を失敗にする |
| 並行取得 | 同時に処理するリージョンと検索 API リクエストが 4 以下である |
| 検索の失敗 | 後続ページまたは別リージョンが失敗しても取得済み行を保持し、EC2 の完全性は false となる |
| SSM の結合 | 成功時の欠落は NotReported、失敗・未取得は Unknown となる |
| 通知の終了 | 遅い読み取りでもページを失わず、最終スナップショットと Done を受け取れる |
| 条件の意味 | Name のワイルドカードと同一キーの複数タグ条件で完全一致・AND を維持する |
| list 出力 | EC2 不完全時の標準出力が空であり、SSM だけの失敗は一覧と警告になる |

API のモックは、ページの返却順、途中の失敗、キャンセル、遅延を指定できるものとする。SDK の HTTP 境界のテストも少数用意し、フィルタと継続トークンが実際のリクエストへ変換されることを確認する。

JSON の配列形式、空結果、欠落値、制御文字、安定順序をこの段階で確定する。以降の内部モデル変更で外部向け JSON を変更しない。

### 4. 対話選択と対象解決の実装

list と同じ inventory を TUI へ接続する。対話・非対話で対象を判定する規則を app に集約し、TUI は選択キーを返す構成とする。

検索途中の表示、フィルタ変更、重複候補、停止中の行、SSM 状態、リージョン別エラーを実装する。Ctrl+R では世代を更新し、古いイベントの破棄と選択維持を実装する。

重要な検証シナリオを、以下に示す。

- 先に届いた 1 件へ自動接続せず、後から届いた同名候補を含めて判定する
- 別リージョンが失敗した場合、非対話解決を失敗にする
- 検索途中でも具体的な running の行は手動選択できる
- 対象省略で開いた一覧では、候補が 1 件でも Enter を待つ
- フィルタの入力で AWS API 呼び出しが増えない
- 対話中のフィルタ編集によって候補が 1 件になっても、自動接続を開始しない
- 更新前のイベントや行から接続先を確定しない
- 連続した更新要求で世代間のワーカーが重ならず、更新中もキャンセルできる
- 標準入力のパイプに渡したバイト列を TUI が消費しない

完了条件は、対話と非対話の両方が同じ ResolvedTarget を生成でき、キャンセル後にワーカーと通知処理が終了することである。

### 5. シェル接続と proxy の実装

session と process を実装し、TUI 終了後に AWS CLI を起動する。次に proxy の直接指定経路と標準ホスト名の名前解決経路を追加する。

まず偽の aws 実行ファイルで引数、環境変数、標準入出力、終了コードを確認する。proxy の標準入出力には NUL を含む任意のバイト列を通し、ssmm が変換や表示を追加しないことを確認する。

完了条件は、通常のシェル接続と AWS-StartSSHSession が実際の EC2 で動作し、ID と --region を渡した proxy で DescribeRegions・EC2・SSM の呼び出しが発生しないことである。SSO 失効、外部コマンド不足、StartSession 拒否、TargetNotConnected は個別に失敗経路を確認する。

StartSession 拒否と TargetNotConnected は、CLI の標準エラー出力の保存と非ゼロ終了を検証する。ssmm 独自の構造化エラーへ分類できることを完了条件にしない。偽の aws に子プロセスも起動させ、OpenSSH からの SIGHUP とラッパーの SIGTERM で子が残存しないことを確認する。

### 6. ssh・scp ラッパーの実装

openssh にユーザー指定、転送指定、起動計画、ProxyCommand の生成を実装する。標準 SSH 設定の生成を必要とせず、コマンドライン引数だけで接続できる状態を先に作る。

偽の ssh・scp と内部 proxy を使い、対象が一度だけ解決されることを確認する。親の選択後に Name やローカル設定が変わっても、内部 proxy へ渡したプロファイル、リージョン、ID、ポートが変わらないことを検証する。

完了条件は、重複 Name の選択後に ssh 接続と scp 送受信が成立し、転送元と転送先のハッシュが一致することである。空白、コロン、先頭ハイフンを含むローカルファイル名、複数ファイル、再帰転送、複数のリモート入力と拒否対象も確認する。

OpenSSH 9.0 以降の SFTP 経路を使い、scp:// URI と空のリモートパスを拒否する。鍵パスの % と ${...}、対話選択だけを禁止した際の OpenSSH の端末操作、既存 IdentityFile との併存を検証する。

### 7. 初期設定と標準 SSH 連携の実装

config の保存処理、sshconfig の生成処理、および init のフォームを実装する。TOML の更新と SSH 設定の生成を分け、入力完了前には書き込まない。

一時ディレクトリに既存の SSH 設定を用意し、先頭の Include、重複排除、Host・Match・コメントの保持、プロファイルの更新と連携解除を検証する。シンボリックリンク、同時更新、ファイル書き込み失敗も確認する。rename される設定ファイル自体をロック対象にせず、専用のロックファイルで init 同士が直列化されることを確認する。各保存地点に失敗を注入し、再実行によって管理用ファイルを修復できることを確認する。

ssh -G は構成したテスト用ファイルに対して実行する。個人の実際の SSH 設定を自動テストの入力にしない。通常の単体テストで AWS へ接続したり ~/.ssh/config を変更したりしない。

完了条件は、標準の ssh・scp・sftp が管理用 SSH 設定だけで動作し、regions の変更が proxy の次回実行に反映されることである。ホスト名で表現できないプロファイルに対する連携要求は、設定を部分更新せずにエラーにする。

### 8. 初版の統合検証と配布準備

受け入れ条件をコマンド全体で確認し、対応環境と外部コマンドの検証済みバージョンを記録する。ビルドは Linux と macOS の対象アーキテクチャで確認し、WSL では Linux バイナリの端末・OpenSSH 連携を確認する。

go test ./...、go test -race ./...、go vet ./... を実行する。PTY を使うプロセステストは Unix のテスト環境で実行し、実 AWS を使うテストは明示的に指定した検証環境で実行する。

配布物には、ビルドしたバイナリ、バージョン情報、チェックサム、必要な外部コマンドと初期設定を説明する利用文書を含める。実行時に依存コマンドや Go の依存モジュールを自動インストールしない。

## 検証の分担

不具合が発生する境界ごとに検証方法を選ぶ。実装の関数をそのまま再現するテストではなく、入力から観測できる結果と失敗時の動作を確認する。

検証方法と対象を、以下にまとめる。

| 検証方法 | 対象 |
| --- | --- |
| 純粋な単体テスト | 完全一致、フィルタ、タグ、設定優先順位、対象指定と scp の文法 |
| 制御可能な取得実装 | ページ途中の失敗、並行数、完全性、キャンセル、古い世代のイベント |
| SDK の HTTP 境界テスト | 実リクエストのフィルタと継続トークン、API エラーの変換 |
| 偽の外部実行ファイル | argv、認証環境、終了コード、proxy のバイト列、再探索の有無 |
| ssh -G と引数記録用 proxy | SSH 設定の解釈、トークン展開、シェルのクォート |
| PTY テスト | パイプ入力と操作端末の分離、Ctrl+C、SIGHUP、SIGTERM、リサイズ、端末復元 |
| 検証用 AWS と EC2 | 認証方式、SSM 接続、SSH ホスト鍵、実際の転送、標準 sftp |

## 実装に反映する決定

外形仕様だけでは実装結果が分かれる事項は、ARCHITECTURE.md で決定する。特に互換性や設定形式へ影響する決定を、以下にまとめる。

| 事項 | 決定 |
| --- | --- |
| 標準 SSH 設定の HostKeyAlias | %h を展開できないため省略し、標準のホスト名で照合する |
| 内部 proxy のプロファイル | 名前と指定元を渡し、AWS CLI での認証の優先順位を維持する |
| 直接指定の探索省略 | proxy の ID + --region に限定する |
| 非対話での対象省略 | 完全な検索結果の候補が 1 件の場合だけ選択する |
| Name と検索条件の併用 | Name、--tag、--filter の AND とする |
| SSH ホスト名の制約 | プロファイルは単一ラベル、TARGET はラベルの連結とする |
| SSH 連携の保存状態 | profiles.PROFILE.ssh.integration を追加する |
| 設定の相対パス | 保存値は設定ファイル基準、フラグ値は作業ディレクトリ基準とする |
| 外部コマンドのエラー | 終了コードと標準エラー出力を保持し、文言の解析で分類しない |
| 起動計画 | execplan の値型を介し、app が実行を依頼する |
| フィルタの編集 | 取得条件から分離し、編集後の選択は Enter を必須とする |
| 取得イベント | ページを破棄せず、集約後の通知だけを最新状態へ置き換える |
| 鍵指定 | ssmm 内の値を上書きし、OpenSSH の他の IdentityFile は併存する |
| proxy の終了 | SIGHUP を捕捉して専用の子プロセスグループを終了する |
| 保存の競合 | 協調する init をロックし、非協調の外部編集との原子性は保証しない |

初期段階で残る確認事項は、ライブラリの固定バージョン、認証方式ごとの実機互換性、OS とシェルごとのプロセス挙動である。これらは実装手順の第 1 段階と第 2 段階で確認し、失敗した組み合わせを対応済みとして公開しない。
